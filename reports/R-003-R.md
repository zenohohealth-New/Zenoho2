## 1. What changed

### The queue no longer needs a network to accept a night

`app/src/backend/sync.ts`. `queueNight(night, remoteCommitmentId)` became `queueNight(night)`,
and it now awaits exactly one thing: the local `enqueue`. The two fields it cannot know on a
phone with the radio off — `commitment_id`, which requires a server round trip, and
`device_clock_offset_min`, which requires a clock probe — are stamped at drain time instead.
Neither is part of the verdict, so neither can change what was derived on device.

A queued-but-unstamped night carries `commitment_id: 0` (`UNSTAMPED_COMMITMENT_ID`). Postgres
identities start at one, so that value is not merely a convention: a row still carrying it has
provably never been uploaded.

### `drainQueue` stopped throwing and stopped needing a round trip to decide

It now returns a `stoppedBecause` string for every ordinary failure — offline, signed out, not
configured, no local commitment — because offline is a normal state of this app, not an
exception. It also asks `auth.getSession()` (reads local storage) rather than `auth.getUser()`
(a request to `/auth/v1/user`). Asking the server whether you are signed in, in order to decide
whether to try the server, is a round trip spent to learn something already on disk.

### One `AppState` listener — the first lifecycle handling in the codebase

`app/App.tsx`. Fires only on `active`, calls the drain, removes itself on unmount. No
react-navigation, no `BackgroundFetch`, no `TaskManager`, no scheduler; a test asserts none of
those four packages appear in `dependencies`, so the constraint outlives this commit.

### Boot no longer mistakes "couldn't check" for "signed out"

The boot effect set `session = null` in a `catch` and then routed to sign-in on `session ===
null`. Offline, `getSession()` failing to confirm a session is not the same fact as there being
none, and the old code could not tell them apart — so a signed-in user opening the app without a
network was liable to be thrown back to sign-in. A `sessionKnown` flag now separates the two, and
sign-in is only forced when the absence of a session is positively established.

This was not in DEF-003-01, and I have not proven it fired on the founder's device. It is a
genuine offline defect found while tracing that path, and it is fixed rather than left.

### Feedback lives next to the control that produces it

`app/src/ui/HistoryScreen.tsx` and the tap handler. Every path through the handler sets a status
line in a `finally`, and it renders beside the button rather than at the top of the screen.

I argued below that this was instrumentation rather than a fix, because on the checker's frame
evidence the handler was never entered. **The device run settled it: AC-R1 PASS.** Whatever kept
the tap out of the handler on `e1a3bdd4` is gone. §3 keeps the reasoning that got this wrong.

## 3. Root cause of the silent no-op

The task asked me to *name the guard that rejected the tap*, and whether the failure was
caught-and-ignored or never thrown. The honest answer is that the premise is wrong, and I would
rather say so than nominate a plausible culprit.

**No guard rejected the tap.** The only guard on that path is `disabled={p.busy}`, and the
handler's first statement is `setBusy(true)`. The net guard (`assertAllowedHost` /
`assertNoRawHealth`) is handed to the Supabase client alone; it is not a global `fetch` override
and cannot see, let alone reject, a button press. Nothing on the tap path calls it.

What I can prove, and what I cannot:

**Proven, caught-and-ignored — the queue.** In `e1a3bdd4`:

```ts
try {
  const { data } = await getSupabase().auth.getUser();   // network round trip
  if (data.user) {
    const remoteId = await ensureRemoteCommitment(c);     // network round trip
    await queueNight(outcome.stored, remoteId);           // ← only reachable online
    await drainQueue();
  }
} catch {
  // Offline, signed out, or refused: the night stays queued for the
  // next foreground (AC-3.6).
}
```

The comment asserts the night stays queued. It does the opposite: `queueNight` is inside the
`try`, after two network calls, so offline the rejection from `getUser()` jumps straight to a
`catch` that does nothing, and **nothing is ever enqueued**. AC-3.6 and AC-R2 were unreachable
by construction. Caught, ignored, and — worse — annotated with a claim that the reader would
have had no reason to doubt.

**Unproven — the missing "Reading…" frame.** I could not reproduce this by reading, and I will
not name a cause I cannot demonstrate. `setBusy(true)` is the first statement and `busy` is
wired to the label, so a tap that reaches the handler should repaint even offline.

I proposed a hypothesis here — that every signal was off-screen, above the fold from the
button — and **the checker rejected it with evidence that settles it.** In the founder's online
screenshot the button *itself* turned grey and its label changed to "Reading…", fully visible.
In the airplane-mode recording that same button stayed solid black across every frame. The
signal that matters was never off-screen; it was co-located with the finger all along.

So DEF-003-01 is **not** a rendering-position problem and **not** the same defect as the
out-of-scope layout item. What the evidence says is narrower and more uncomfortable: `busy`
never became true, which means **`setBusy(true)` never ran, which means the handler never
started.** The tap did not reach `onPress`.

**That was my reading, and the device disagreed with it.** AC-R1 PASSED on `2eb5c840`: offline,
the tap enters the handler, the button greys, a verdict appears. So the cause was somewhere in
what this change replaced after all — the rewritten handler, the removed network calls on the
tap path, or the boot routing — and my inference from "busy never became true" to "the tap never
arrived" skipped a step I could not see from here.

Two wrong turns on one defect, both left standing above: first the above-the-fold hypothesis,
then this. The lesson is the same one D-038 already encodes — a device run decides, and reading
code carefully is not a substitute for it, however confident the reading feels.

The status line I added is therefore not the fix; it is instrumentation. If the next run shows
"Reading your watch…" appear offline, the handler is being entered and the old build's silence
had some other explanation. If the line stays blank while the button stays black, the handler is
still not being entered and the fault is upstream of all of this — in the Pressable, the
ScrollView's touch handling, or the JS thread. Either outcome is conclusive, which is why AC-R1
must be photographed and why I am not claiming DEF-003-01 as fixed.

## 4. Did derivation itself have a server dependency?

**No. Only the upload did.** Stated plainly, as asked.

`deriveAndStoreNight` reaches exactly two things: the `HealthStore` (Health Connect, on-device)
and SQLite. It imports nothing from `src/backend` and calls no `fetch`. The verdict, the
revision and freeze rules, the wear-presence ratio and the RHR coherence check are all pure
TypeScript over local data. D-010 is intact and was never at risk.

This is now enforced rather than merely true: `tests/offline-sync.test.ts` fails if
`nightlyEngine.ts` or the `derive` layer gains an import from `src/backend` or `src/net`. The
property was previously a fact about the current call order; it is now a fact about the design.

**No design defect to escalate on this point.** The defect was that a *local* operation —
queueing — had been placed behind a *remote* one.

## 7. AC-3.5 — closed at the key level; AC-3.5-v carried forward as a launch gate

**Checker ruling, 2026-09-09: the key-level proof is accepted as sufficient to close T-003.**

### What could not be done, and why the original plan was wrong

The task proposed reading request bodies from the Supabase logs. That is not possible: Supabase
does not retain request bodies. `edge_logs` holds method, path, status and headers, and the CLI
has no `logs` command at all. No amount of digging would have produced a verbatim body, so the
fallback was not a shortcut — it was the only thing available short of a proxy.

### What was proven instead, against the live project

Three requests to the real PostgREST endpoint on `kjmaivclilrovfvqvjqr`:

```
A)  body containing "bpm"      -> HTTP 400
    {"code":"PGRST204","message":"Could not find the 'bpm' column of 'daily_states' in the schema cache"}

A2) body containing "startMs"  -> HTTP 400
    {"code":"PGRST204","message":"Could not find the 'startMs' column of 'daily_states' in the schema cache"}

B)  body with valid columns only -> HTTP 401
    {"code":"42501","message":"new row violates row-level security policy for table \"daily_states\""}
```

**The ordering is the finding.** PostgREST validates the payload's columns *before* it applies
authorization: A and A2 die at the schema, B survives the schema and only then hits RLS. So a
body carrying an HR sample, an RHR value, or an epoch-ms timestamp under any of the guard's
forbidden keys is refused with 400 and writes nothing.

Row 30 exists (§7a). Therefore the device's actual request body contained only keys that are
columns of `daily_states` — and that table has no column able to hold a timestamp, an HR sample
or an RHR value. `computed_at` is server-set; `device_clock_offset_min` is an integer count of
minutes (D-034).

This is evidence about the real device request, from the real server, and it is stronger than
the guard's 15/15 against synthetic payloads — which the task rightly refused to accept.

### What it does NOT prove — AC-3.5-v

It constrains the body's **keys**, not its **values**. A timestamp smuggled inside `source_id`
would pass every check above. On this night `source_id` was null, so nothing was smuggled — but
a NO_DATA night is the weakest possible case: no source, no deviation, almost nothing sent. A
KEPT night with a real wearable is where a leak would actually show, and none has been captured.

**AC-3.5-v · value-level proof · LAUNCH GATE, not a T-003 gate.** Proxy the phone (mitmproxy on
the laptop, phone Wi-Fi pointed at it, CA certificate installed on the device) and capture one
**KEPT** night's upload. Paste the body verbatim and confirm it carries no timestamp inside the
sleep window, no HR value and no RHR value. **This must pass before any invite goes out**, and it
is recorded as such in CLAUDE.md's External contracts so a later session cannot miss it.
