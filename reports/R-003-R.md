## 1. What changed

### The queue no longer needs a network to accept a night

`app/src/backend/sync.ts`. `queueNight(night, remoteCommitmentId)` became `queueNight(night)`,
and it now awaits exactly one thing: the local `enqueue`. The two fields it cannot know on a
phone with the radio off — `commitment_id`, which requires a server round trip, and
`device_clock_offset_min`, which requires a clock probe — are stamped at drain time instead.
Neither is part of the verdict, so neither can change what was derived on device.

A queued-but-unstamped night carries `commitment_id: 0` (`UNSTAMPED_COMMITMENT_ID`). Postgres
identities start at one, so that value is not merely a convention: a row still carrying it has
provably never been uploaded.

### `drainQueue` stopped throwing and stopped needing a round trip to decide

It now returns a `stoppedBecause` string for every ordinary failure — offline, signed out, not
configured, no local commitment — because offline is a normal state of this app, not an
exception. It also asks `auth.getSession()` (reads local storage) rather than `auth.getUser()`
(a request to `/auth/v1/user`). Asking the server whether you are signed in, in order to decide
whether to try the server, is a round trip spent to learn something already on disk.

### One `AppState` listener — the first lifecycle handling in the codebase

`app/App.tsx`. Fires only on `active`, calls the drain, removes itself on unmount. No
react-navigation, no `BackgroundFetch`, no `TaskManager`, no scheduler; a test asserts none of
those four packages appear in `dependencies`, so the constraint outlives this commit.

### Boot no longer mistakes "couldn't check" for "signed out"

The boot effect set `session = null` in a `catch` and then routed to sign-in on `session ===
null`. Offline, `getSession()` failing to confirm a session is not the same fact as there being
none, and the old code could not tell them apart — so a signed-in user opening the app without a
network was liable to be thrown back to sign-in. A `sessionKnown` flag now separates the two, and
sign-in is only forced when the absence of a session is positively established.

This was not in DEF-003-01, and I have not proven it fired on the founder's device. It is a
genuine offline defect found while tracing that path, and it is fixed rather than left.

### Feedback lives next to the control that produces it

`app/src/ui/HistoryScreen.tsx` and the tap handler. See §3 — this is the part that explains the
observation, and the reasoning is worth reading before the code.

## 3. Root cause of the silent no-op

The task asked me to *name the guard that rejected the tap*, and whether the failure was
caught-and-ignored or never thrown. The honest answer is that the premise is wrong, and I would
rather say so than nominate a plausible culprit.

**No guard rejected the tap.** The only guard on that path is `disabled={p.busy}`, and the
handler's first statement is `setBusy(true)`. The net guard (`assertAllowedHost` /
`assertNoRawHealth`) is handed to the Supabase client alone; it is not a global `fetch` override
and cannot see, let alone reject, a button press. Nothing on the tap path calls it.

What I can prove, and what I cannot:

**Proven, caught-and-ignored — the queue.** In `e1a3bdd4`:

```ts
try {
  const { data } = await getSupabase().auth.getUser();   // network round trip
  if (data.user) {
    const remoteId = await ensureRemoteCommitment(c);     // network round trip
    await queueNight(outcome.stored, remoteId);           // ← only reachable online
    await drainQueue();
  }
} catch {
  // Offline, signed out, or refused: the night stays queued for the
  // next foreground (AC-3.6).
}
```

The comment asserts the night stays queued. It does the opposite: `queueNight` is inside the
`try`, after two network calls, so offline the rejection from `getUser()` jumps straight to a
`catch` that does nothing, and **nothing is ever enqueued**. AC-3.6 and AC-R2 were unreachable
by construction. Caught, ignored, and — worse — annotated with a claim that the reader would
have had no reason to doubt.

**Unproven — the missing "Reading…" frame.** I could not reproduce this by reading, and I will
not name a cause I cannot demonstrate. `setBusy(true)` is the first statement and `busy` is
wired to the label, so a tap that reaches the handler should repaint even offline.

My best-supported hypothesis, offered as a hypothesis: **every signal was off-screen.** The
verdict and the error banner both render at the top of a `ScrollView`; the button sits below a
thirty-row list. From the button, all of it is above the fold. The founder independently logged
"Check last night sits below a 30-row list and the founder could not find it" as a separate
defect — which is evidence for this reading, not against it. If that is what happened, then the
layout defect ruled out of scope and DEF-003-01 are the same defect seen from two angles.

I have not moved the button, per scope. I have put the feedback where the finger is, which the
scope explicitly requires ("A tap must never produce zero visual feedback… Silence is not an
acceptable outcome in any code path") and which an error message thirty rows away does not
satisfy. **This is the part of the fix I am least able to guarantee, and the next device run
should treat it as the open question.**

## 4. Did derivation itself have a server dependency?

**No. Only the upload did.** Stated plainly, as asked.

`deriveAndStoreNight` reaches exactly two things: the `HealthStore` (Health Connect, on-device)
and SQLite. It imports nothing from `src/backend` and calls no `fetch`. The verdict, the
revision and freeze rules, the wear-presence ratio and the RHR coherence check are all pure
TypeScript over local data. D-010 is intact and was never at risk.

This is now enforced rather than merely true: `tests/offline-sync.test.ts` fails if
`nightlyEngine.ts` or the `derive` layer gains an import from `src/backend` or `src/net`. The
property was previously a fact about the current call order; it is now a fact about the design.

**No design defect to escalate on this point.** The defect was that a *local* operation —
queueing — had been placed behind a *remote* one.

## 9. Status, assumptions, risks

**Status: NOT_DONE.** Not IN_REVIEW, per D-040: no screen has been manually exercised, because
this machine cannot exercise one.

**Assumptions, each of which could be wrong:**

1. That co-locating feedback addresses DEF-003-01. If the tap genuinely never reached the
   handler, this change will not fix it — and the next run will show that, because the status
   line will stay blank where the old build showed nothing.
2. That `getSession()` resolves offline from local storage rather than blocking on a refresh.
   Behaviour under an expired token with no network is asserted from the supabase-js contract,
   not observed.
3. That `commitment_id: 0` never collides. True for Postgres identity columns; it would stop
   being true if the column were ever backfilled by hand.

**Risks:**

- **The one that matters:** two of the three fixes are structurally verified but behaviourally
  unproven. The queue fix I would defend strongly — the old code path is plainly unreachable
  offline. The visual-feedback fix rests on a hypothesis I could not confirm.
- The `sessionKnown` boot change alters routing for signed-in users offline. It is a strict
  improvement in intent, and it is not covered by any automated test, because the boot effect
  is not reachable from vitest.
- Resend still delivers only to zenohohealth@gmail.com (D-039). Unchanged, and blocking for
  anyone but the founder.

**Recommended next step:** confirm the build, then run AC-R1 first and photograph the status line
under the button. That single observation settles §3's open question either way, and everything
else in the run depends on it.
