## 2. Eligibility (D-042)

### What the rule is now

```
manual entry            -> INELIGIBLE
anything else           -> ELIGIBLE
```

That is the whole of `classifySource`. `sourceId` is recorded verbatim and never compared against
anything. `SourceClass` drops from three values to two: there is no `UNKNOWN` any more, because
"unknown" was only ever a statement about a list that no longer exists.

`brandUnverified` is deleted everywhere, which removes a real behaviour: an unrecognised brand
used to force `integrity = UNVERIFIED` on an otherwise good night. Under D-042 there is nothing
for that flag to mean. `integrity` can still be downgraded by RHR incoherence (L3), which is a
data-quality judgement and untouched.

### Why the brand lists were worse than they looked

Deleting them is not only a policy change. Every id in that file was a **guessed package string** —
the file's own note said so: *"MOST IDENTIFIER STRINGS BELOW ARE STILL UNVERIFIED."* So a correct,
listed brand whose real package differed by one character landed in exactly the same bucket as a
brand nobody had heard of. The list gave the *appearance* of a curated allowlist while behaving,
for most entries, like no list at all. Only one string in it was ever confirmed against a device
(Garmin, R-001 run 2).

The Android `block` list, meanwhile, had **one** entry: `com.google.android.apps.healthdata`, the
Health Connect app itself. Not Samsung Health, not Google Fit. So the thing everyone assumed was
keeping phone-inferred sleep out — a blocklist of phone apps — did not exist. See §2b.

### 2b. The phone exclusion: what was actually enforcing it (AC-5.1b)

D-003's phone rule survives D-042, and the task was right to insist on it. But tracing the code,
**the brand list was never what enforced it.** Samsung Health is not on any list; under the old
rule it classified as `UNKNOWN`, and `UNKNOWN` was eligible *if the session carried heart rate*.
A phone with no watch paired produces no overnight HR, so it failed there — on the data.

So the mechanism was already non-brand. T-005 makes it the explicit and only rule, and applies it
uniformly:

```ts
// eligible only if HR from THIS SESSION'S OWN source covers it (D-045)
function hasOwnSourceHr(session, hr, platform): boolean
```

The "own source" qualifier is not decoration and was not in the first version of this code. It is
DEF-005-01, and §11.1 is the account of it.

This is now required of **every** source, not only unrecognised ones. The old rule trusted a
listed brand without HR — lenient exactly where a guessed package string was most likely to be
wrong.

**Why this is the right discriminator, and not a workaround.** A phone has no sensor that can
measure heart rate through a night. "HR is present across this session, from a source that is
itself eligible" is therefore something phone-inferred sleep cannot fake, and it is a property of
the data rather than a claim about identity. Naming Samsung Health would have been strictly
worse: **the same package writes watch-derived sleep when a Galaxy Watch is paired and
phone-derived sleep when one is not**, so the package name cannot separate the two even in
principle. A blocklist entry would have refused every Galaxy Watch user in the gym. There is a
test for exactly that pair — same package, ineligible without HR, eligible with it.

### What it does not prove, and what it would take

The honest limit: this is a proxy. It says "accompanied by a signal a phone cannot produce", not
"came from a wrist". A phone app that relayed HR from elsewhere would pass — though if it is
relaying real HR, something on a wrist produced it.

The principled alternative is Health Connect's own `Metadata.device.type`, and I checked whether
it is usable before settling for the proxy. **It is not, yet, for three reasons:**

1. **`device` and `device.type` are both optional** in the record metadata, and are commonly left
   unset by writing apps.
2. **The binding's enum has no watch.** `react-native-health-connect`'s `DeviceType` is
   `TYPE_UNKNOWN=0, TYPE_PHONE=2, TYPE_SCALE=3, TYPE_RING=4, TYPE_HEAD_MOUNTED=5,
   TYPE_FITNESS_BAND=6, TYPE_CHEST_STRAP=7, TYPE_SMART_DISPLAY=8`. **Value 1 is missing** — the
   platform's `TYPE_WATCH`. The single device class that matters most here has no named constant
   in the library we depend on.
3. **We have never observed it.** `SleepSession` does not carry device metadata at all, so
   nothing in this project knows whether a Garmin Vívoactive 5 populates it on the founder's
   phone. Building a gate on a field we have never seen a value for is the mistake D-003's
   package strings already made once.

**Recommendation, not implemented here:** capture `metadata.device` on the next device run and
record what real sources actually report. If watches populate it, a device-type gate becomes a
defensible addition *alongside* the HR rule. Until then the HR rule stands alone, and it is
better evidence than a name.

## 3. F3 — a real bug, found before the device run

The T-003-R boot code:

```ts
const { data } = await getSupabase().auth.getSession();
session = data.session;
sessionKnown = true;          // ← wrong
```

`sessionKnown` was added in T-003-R precisely so that "couldn't check" would not read as "signed
out". It only handled the *throwing* case. **supabase-js does not throw when it cannot refresh:**
with an expired access token and no network, `getSession()` returns
`{ data: { session: null }, error: AuthRetryableFetchError }`. The `catch` never fires,
`sessionKnown` is set true, `session` is null — and the boot routes a signed-in member to the
sign-in screen. Exactly the failure the flag was introduced to prevent, one layer down.

Fixed:

```ts
const { data, error } = await getSupabase().auth.getSession();
session = data.session;
sessionKnown = error === null;
```

AC-5.6 would have failed on the device. It cost nothing to find here and would have cost a
round trip and an hour of waiting to find there — which is the whole of D-038's argument.

Worth stating: this is the second time in this project that a `catch`-only error path has hidden
a non-throwing failure. The first was `queueNight` behind `auth.getUser()`. Both were "the
library reports failure by returning, not by throwing".

## 11. AUDIT-01 — four defects fixed, three logged

### 11.1 DEF-005-01 — HR had to come from the session's own source (D-045)

The defect the checker found, and it is the most serious thing in this report. §2b argued that
requiring heart rate was a sound phone exclusion because a phone cannot measure HR overnight.
That argument was right. **The implementation did not enforce it**, because it asked only whether
*some* eligible HR overlapped the session window:

```ts
hr.some((h) => h.atMs >= session.startMs && h.atMs < session.endMs && eligible(h))
```

On a night when the member wore a watch **and** their phone inferred sleep from screen-off time,
the phone's session matched on the watch's heart rate. The two records share nothing but a clock.

And it was worse than a false positive, because the phone's inferred session is typically the
*longer* of the two: it won `selectMainSession`, became the night, and was derived from
phone-inferred bed and wake times with `integrity = OK`. The exclusion that D-042 was careful to
preserve failed on precisely the nights it was written for. My §2b reasoning was sound and my
code did not implement it — the gap between those two is the lesson, not the rule itself.

**Fixed in three places**, all of which had the same bug independently:
`hasOwnSourceHr` (source ids must match), the `acceptHrSource` predicate handed to
`wearPresence`, and `selectMainSession`, which now takes `hr` as a **required** argument so a new
call site cannot skip the check.

**New integrity value `NO_HR`**, distinct from both neighbours:

| Value | Means |
|---|---|
| `NO_SOURCE` | no eligible sleep session at all |
| `NO_HR` | a session arrived; its own source sent no heart rate across it |
| `NO_WEAR` | own-source HR exists but covers under 70% of the session |

Not cosmetic: reporting NO_HR as NO_SOURCE told a member no wearable was seen on a night when one
had written a session all night, sending them to look in the wrong place.

**APPLIED 2026-09-14, and verified.** The checker gave MIGRATION GO; the paragraph below is left
as written because it states the risk that existed, and the verification follows it.

```
supabase db push      -> Applying migration 20260913000003_no_hr_integrity.sql ... Finished
supabase migration list -> 20260908000001 | 20260908000002 | 20260913000003   (all local = remote)
```

`backend/tests/no_hr_integrity.sql`, run against the live project, 4/4:

```
1  insert integrity = NO_HR                      PASS: accepted
2  the NO_HR row reads back intact               PASS: 1 row, state NO_DATA, deviation_min null
3  a value outside the ladder ('BANANA')         PASS: check refused
4  the five pre-existing values still accepted   PASS: all 5
```

Check 3 is the one that matters. Showing NO_HR is accepted proves nothing on its own — a dropped
constraint would accept it too, and would accept anything else. The negative control is what
shows the constraint still exists and was widened rather than removed. The whole thing runs in a
transaction that is rolled back, so no test row survives in the founder's data.

**The blocker as it stood before that run:**
`daily_states.integrity` carries a CHECK constraint that does not list `NO_HR`, so the app now
produces a value the server refuses. `backend/supabase/migrations/20260913000003_no_hr_integrity.sql`
extends it, idempotently. **Until it is applied, every NO_HR night is rejected with a 400 and
re-queues forever** — retried on each foreground, failing identically, with nothing on screen to
explain why. I have not applied it: D-036 gates commands against the external project behind a
printed identity *and* founder confirmation, and AUDIT-01 gave BUILD GO, not migration GO. The

### 11.2 DEF-005-02 — the commitments insert goes through a whitelist

`toServerCommitment()` now sits beside `toServerRow()` in `app/src/net/payload.ts`, constructive
in the same way: four named fields copied one at a time.

Nothing raw lives on a commitment today, which is exactly why this was easy to miss. The risk is
`StoredCommitment` growing a field — a device id, a created-at, a nickname — that a spread or an
absent-minded `...local` then carries to the server. The network guard would not have caught any
of those: a device id is just a string, and a created-at in seconds was not a timestamp the guard
recognised until 11.3. **This was the last write path in the app built inline.**

### 11.3 DEF-005-03 — epoch seconds, and a second hole the test exposed

`EPOCH_SEC = /\b1[0-9]{9}\b/` joins the millisecond pattern. The guard knew milliseconds only,
so `Math.floor(Date.now() / 1000)` — the most ordinary way there is to shrink a timestamp —
walked through the check whose whole purpose is to stop timestamps.

**Writing the test for it found a second, older defect.** `guardedFetch` falls back to scanning
the raw body when it is not JSON, and that fallback lands in `walk`'s *string* branch, which only
ever applied the ISO pattern. So a non-JSON body reading `ts=1757206800000` passed the guard —
and that hole predates this task and swallowed **milliseconds** just as happily. The string
branch now tests both epoch patterns as well. Two tests cover it, one per unit.

A check on the other side: the §7 row's real integers are minutes (`deviation_min`,
`device_clock_offset_min`), a small identity (`commitment_id`) and booleans. None is ten digits
beginning with 1, and a test asserts a realistic row still passes.

**netguard 15 → 23.**

## 9. Assumptions, risks, recommended next step

**Assumptions:**

1. That a phone cannot produce overnight heart rate. This is what the phone exclusion rests on
   now. True of every phone I am aware of; it would fail if a phone app synthesised HR, or
   relayed it from a source Zenoho then credits to the phone app.
2. That `getSession()` sets `error` on a failed refresh rather than returning a bare null. This
   is the fix in §3 and it is **asserted from the supabase-js contract, not observed** — AC-5.6
   is exactly the test of it.
3. That no beta member has a wearable whose app writes sleep but never heart rate. Such a device
   is now silently ineligible with no explanation beyond the No-data hint.

**Risks:**

- **The D-045 migration gap is the live one.** Code and schema disagree right now. The failure is
  silent from the member's side — a night that never syncs, retried forever.
- **DEF-005-01 is the second time in this task that reasoning I was confident in was not what the
  code did.** §2b's argument for the HR rule was correct and the implementation did not honour
  it; the checker found that by reading, not by running. Nothing in the suite would have caught
  it, because every eligibility test used a single source, where "own source" and "any source"
  are the same thing. The new tests use two.
- **Assumption 3 is the one to watch.** D-042 widens the gate on brand and this task narrows it
  on HR, uniformly, for the first time. A device that writes sleep without HR used to be eligible
  if its brand was listed; now it is not. I believe that is correct — a night with no HR has no
  wear check and no integrity — but it is a real behaviour change in the opposite direction to
  D-042's intent, and the checker should see it stated rather than discover it from a support
  message.
- Two consecutive defects have been "the library reports failure by returning, not throwing"
  (§3). Nothing systematically audits the other places this app calls a library and reads only
  the happy path.
- AC-3.5-v remains a **launch gate** and is untouched by this task.

**Recommended next step: apply the D-045 migration before anything else** (§11.1). It is one
command, and without it the build in §12 writes NO_HR nights that the server refuses forever.
Then run AC-5.6 first among the device criteria: it covers the one fix asserted from a library
contract rather than observed, and it is the only one that can still send a signed-in member back
to a sign-in screen they cannot complete offline.

## 13. DEF-005-05 — skipped nights were never derived

Founder's device, build `b8878ba5`, fresh install 14 Sep. The 30-night list showed Mon 14 Sep and
then Wed 9 Sep. Thu 10 – Sun 13 were **absent** — not four No-data rows, four missing rows —
while Health Connect held the sleep for all four. The daily reminder fired on each of those
mornings and derived nothing.

### Cause

Derivation only ever targeted **last night**, plus a first-run backfill gated on the local store
being completely empty:

```ts
if ((await countNights(c.id)) === 0) await backfill(base);   // fresh install only
const outcome = await deriveAndStoreNight({ ...base, nightDate: today });
```

So once a single night existed, the backfill never ran again, and any night the member did not
open the app for was never derived by anything. The gap was permanent: nothing in the app ever
looked back.

**An absent row is worse than a No-data row**, and that is the part that makes this more than a
cosmetic bug. A No-data row says "we looked and found nothing". An absent row is
indistinguishable from a night that never happened — so skipping the app quietly erased the
evidence, which is the exact opposite of what an accountability product is for.

### Fix

`catchUpMissingNights()` in `app/src/engine/nightlyEngine.ts`. On open **and** on Check last
night, every night in the 30-night window with no local row is derived, oldest first, and queued
for upload like any other.

- **Oldest first**, because `applyRevision` compares each night against what is already stored and
  the §5 freeze rules read forward in time.
- **Nights before the promise start are excluded.** A commitment made on the 10th says nothing
  about the 8th; deriving past it would invent a verdict against a promise that did not exist.
  `StoredCommitment.createdAt` is the cut.
- **It subsumes the old backfill.** On a fresh install every night in the window is missing, so
  the same loop fills them. The "is this the first run" branch is gone rather than fixed — it was
  the branch that made "derive everything" conditional on the wrong thing.
- **A failed read stays absent.** `deriveAndStoreNight` returning null means Health Connect
  errored, and that is not a night the member missed; it is counted as `unreadable` and retried
  next time. A night that genuinely holds no sleep is a different case and is written as NO_DATA.
- **Recovered nights are queued too**, not just last night, or the server would keep precisely the
  hole the local history just lost.

### A second gap found while fixing this: the warm resume

Worth separating out, because it is the one that made the reminder useless. The boot effect
derives on a **cold** start. The `AppState` listener, which is what a **warm** resume reaches,
only drained the upload queue — it derived nothing. So tapping the morning reminder on an app
still in memory did not derive last night. The reminder whose entire purpose is to make you check
last night did not, itself, check last night.

The listener now runs the same `sync` the button does. The catch-up is cheap once there is
nothing to catch up: one read of the stored night dates, then a set lookup per night.

### How long a 4-night catch-up takes on the founder's phone

**Not measured, and I cannot measure it** — this machine has no device, and the cost is dominated
by Health Connect reads whose speed is a property of the phone. So it is instrumented rather than
guessed: `CatchUpResult.elapsedMs` is timed around the loop and **printed in the status line**
whenever nights are recovered — *"Also caught up 4 nights you missed (2.3s)."*

That number will be on screen on the next device run. Reporting a figure from a laptop would have
been a fabrication, and this is the shape that makes it obtainable instead.

### Does tapping the daily reminder trigger a derive?

**Now yes, on both paths; before this fix, only on a cold start.** Tapping the notification opens
the app — a cold start runs the boot effect, which derives; a warm resume reached only the
`AppState` listener, which drained the upload queue and derived nothing. The notification
listeners themselves have never derived: they call `recordMorningSyncFired()` and nothing else.

### Logged for T-004B, not implemented

**A night with no server row after its freeze time must surface to the witness as a distinct
"not reported" state, never as an absent row.** Skipping the app must not hide a night. This is
the server-side half of the same principle: the local fix stops the member's own history lying to
them, and this stops it lying to their witness. Thesis-level — an accountability product in which
not showing up is indistinguishable from not existing has no mechanism at all. **Not implemented
here**, as instructed.

`tests/engine.test.ts`, engine 11 → 17. The checker's case verbatim: a 5-night gap yields 5 rows,
