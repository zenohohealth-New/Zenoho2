## 2. Eligibility (D-042)

### What the rule is now

```
manual entry            -> INELIGIBLE
anything else           -> ELIGIBLE
```

That is the whole of `classifySource`. `sourceId` is recorded verbatim and never compared against
anything. `SourceClass` drops from three values to two: there is no `UNKNOWN` any more, because
"unknown" was only ever a statement about a list that no longer exists.

`brandUnverified` is deleted everywhere, which removes a real behaviour: an unrecognised brand
used to force `integrity = UNVERIFIED` on an otherwise good night. Under D-042 there is nothing
for that flag to mean. `integrity` can still be downgraded by RHR incoherence (L3), which is a
data-quality judgement and untouched.

### Why the brand lists were worse than they looked

Deleting them is not only a policy change. Every id in that file was a **guessed package string** —
the file's own note said so: *"MOST IDENTIFIER STRINGS BELOW ARE STILL UNVERIFIED."* So a correct,
listed brand whose real package differed by one character landed in exactly the same bucket as a
brand nobody had heard of. The list gave the *appearance* of a curated allowlist while behaving,
for most entries, like no list at all. Only one string in it was ever confirmed against a device
(Garmin, R-001 run 2).

The Android `block` list, meanwhile, had **one** entry: `com.google.android.apps.healthdata`, the
Health Connect app itself. Not Samsung Health, not Google Fit. So the thing everyone assumed was
keeping phone-inferred sleep out — a blocklist of phone apps — did not exist. See §2b.

### 2b. The phone exclusion: what was actually enforcing it (AC-5.1b)

D-003's phone rule survives D-042, and the task was right to insist on it. But tracing the code,
**the brand list was never what enforced it.** Samsung Health is not on any list; under the old
rule it classified as `UNKNOWN`, and `UNKNOWN` was eligible *if the session carried heart rate*.
A phone with no watch paired produces no overnight HR, so it failed there — on the data.

So the mechanism was already non-brand. T-005 makes it the explicit and only rule, and applies it
uniformly:

```ts
// eligible only if HR from an eligible source covers the session
function hasOwnSourceHr(session, hr, platform): boolean
```

This is now required of **every** source, not only unrecognised ones. The old rule trusted a
listed brand without HR — lenient exactly where a guessed package string was most likely to be
wrong.

**Why this is the right discriminator, and not a workaround.** A phone has no sensor that can
measure heart rate through a night. "HR is present across this session, from a source that is
itself eligible" is therefore something phone-inferred sleep cannot fake, and it is a property of
the data rather than a claim about identity. Naming Samsung Health would have been strictly
worse: **the same package writes watch-derived sleep when a Galaxy Watch is paired and
phone-derived sleep when one is not**, so the package name cannot separate the two even in
principle. A blocklist entry would have refused every Galaxy Watch user in the gym. There is a
test for exactly that pair — same package, ineligible without HR, eligible with it.

### What it does not prove, and what it would take

The honest limit: this is a proxy. It says "accompanied by a signal a phone cannot produce", not
"came from a wrist". A phone app that relayed HR from elsewhere would pass — though if it is
relaying real HR, something on a wrist produced it.

The principled alternative is Health Connect's own `Metadata.device.type`, and I checked whether
it is usable before settling for the proxy. **It is not, yet, for three reasons:**

1. **`device` and `device.type` are both optional** in the record metadata, and are commonly left
   unset by writing apps.
2. **The binding's enum has no watch.** `react-native-health-connect`'s `DeviceType` is
   `TYPE_UNKNOWN=0, TYPE_PHONE=2, TYPE_SCALE=3, TYPE_RING=4, TYPE_HEAD_MOUNTED=5,
   TYPE_FITNESS_BAND=6, TYPE_CHEST_STRAP=7, TYPE_SMART_DISPLAY=8`. **Value 1 is missing** — the
   platform's `TYPE_WATCH`. The single device class that matters most here has no named constant
   in the library we depend on.
3. **We have never observed it.** `SleepSession` does not carry device metadata at all, so
   nothing in this project knows whether a Garmin Vívoactive 5 populates it on the founder's
   phone. Building a gate on a field we have never seen a value for is the mistake D-003's
   package strings already made once.

**Recommendation, not implemented here:** capture `metadata.device` on the next device run and
record what real sources actually report. If watches populate it, a device-type gate becomes a
defensible addition *alongside* the HR rule. Until then the HR rule stands alone, and it is
better evidence than a name.

## 3. F3 — a real bug, found before the device run

The T-003-R boot code:

```ts
const { data } = await getSupabase().auth.getSession();
session = data.session;
sessionKnown = true;          // ← wrong
```

`sessionKnown` was added in T-003-R precisely so that "couldn't check" would not read as "signed
out". It only handled the *throwing* case. **supabase-js does not throw when it cannot refresh:**
with an expired access token and no network, `getSession()` returns
`{ data: { session: null }, error: AuthRetryableFetchError }`. The `catch` never fires,
`sessionKnown` is set true, `session` is null — and the boot routes a signed-in member to the
sign-in screen. Exactly the failure the flag was introduced to prevent, one layer down.

Fixed:

```ts
const { data, error } = await getSupabase().auth.getSession();
session = data.session;
sessionKnown = error === null;
```

AC-5.6 would have failed on the device. It cost nothing to find here and would have cost a
round trip and an hour of waiting to find there — which is the whole of D-038's argument.

Worth stating: this is the second time in this project that a `catch`-only error path has hidden
a non-throwing failure. The first was `queueNight` behind `auth.getUser()`. Both were "the
library reports failure by returning, not by throwing".

## 9. Assumptions, risks, recommended next step

**Assumptions:**

1. That a phone cannot produce overnight heart rate. This is what the phone exclusion rests on
   now. True of every phone I am aware of; it would fail if a phone app synthesised HR, or
   relayed it from a source Zenoho then credits to the phone app.
2. That `getSession()` sets `error` on a failed refresh rather than returning a bare null. This
   is the fix in §3 and it is **asserted from the supabase-js contract, not observed** — AC-5.6
   is exactly the test of it.
3. That no beta member has a wearable whose app writes sleep but never heart rate. Such a device
   is now silently ineligible with no explanation beyond the No-data hint.

**Risks:**

- **Assumption 3 is the one to watch.** D-042 widens the gate on brand and this task narrows it
  on HR, uniformly, for the first time. A device that writes sleep without HR used to be eligible
  if its brand was listed; now it is not. I believe that is correct — a night with no HR has no
  wear check and no integrity — but it is a real behaviour change in the opposite direction to
  D-042's intent, and the checker should see it stated rather than discover it from a support
  message.
- Two consecutive defects have been "the library reports failure by returning, not throwing"
  (§3). Nothing systematically audits the other places this app calls a library and reads only
  the happy path.
- AC-3.5-v remains a **launch gate** and is untouched by this task.

**Recommended next step:** confirm the build, then run AC-5.6 first. It is the one AC covering a
fix that is asserted from a library contract rather than observed, and it is the only one that
can still send a signed-in member back to a sign-in screen they cannot complete offline.
