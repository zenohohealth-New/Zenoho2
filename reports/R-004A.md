## 2. The witness projection, and why a function rather than a view

**Mechanism: a `security definer` function, `public.witness_nights(p_member uuid)`, returning
`(night_date date, state text, streak integer)`. The witness has no SELECT policy on
`daily_states` at all.**

The constraint is that `deviation_min` must be unreadable by a witness, while `state` must be
readable — two columns of the same row, in opposite directions. RLS cannot express that, because
a policy admits or denies whole rows.

I considered a view and rejected it. A view would still have to read `daily_states` as somebody
permitted to read it, and `daily_states` carries `force row level security`, so a view owned by
the table owner is subject to the same policies and returns nothing. Making a view work would
require either an owner with `BYPASSRLS` or a witness `SELECT` policy on `daily_states` — and
that second option is precisely the thing that must not exist. The moment a witness can select
that table, `deviation_min` is one `select *` away, and the privacy guarantee degrades into "no
query we have written so far asks for it".

The function inverts the default. **The witness's access to `daily_states` is nil; the only door
is the function, and the function's return type is the whitelist.** A column added to
`daily_states` next month cannot appear in its output, because the signature does not name it.
That is the same reasoning as `toServerRow` on the device (D-010): construct the permitted shape,
never redact the forbidden one — a whitelist fails closed, a redaction fails open.

**AC-4A.3 — the returned columns, from the function signature:**

```
night_date  date
state       text
streak      integer
```

Three columns. Not `deviation_min`, not `integrity`, not `source_id`, not `wear_presence`, not
`frozen`, not `commitment_id`, not `computed_at`, not `device_clock_offset_min`. Two checks in
the test suite assert this against `pg_proc` rather than against my word for it: check 4 asserts
the projected column list equals exactly `night_date,state,streak`, and check 26 separately
asserts the absence of each of the four forbidden names.

**One decision inside the projection, now ruled on.** `state` on the device has four values:
KEPT, MISSED, NO_DATA and TRAVEL (D-016). D-005 grants the witness three. TRAVEL is not among
them, so the projection maps TRAVEL → NO_DATA — granting only what is listed. **Confirmed for
v1 by the checker on 2026-09-08.**

## 3. Streak: computed on read

**Decision: computed on read, from `daily_states`. No stored counter.**

The task asked me to prefer this unless there was a concrete reason not to, and I did not find
one. The reasons for it are stronger than the convenience of a column:

- A stored counter is a second source of truth. The device already computes a streak
  (`cycleStreak` in `app/src/derive/index.ts`), and D-010 makes the device authoritative. A
  server-side counter would be a third number that can disagree with both.
- Nights are revisable until the freeze (spec §5). A stored counter would need every revision to
  correctly rewrite history behind it; computing on read makes revision automatic.
- The volume does not justify it. A cycle is 28 rows per member. This is a loop over at most 28
  rows on a request that happens a few times a day per witness.

**It mirrors `cycleStreak()` exactly**: iterate nights ascending, KEPT increments, MISSED resets
to zero, NO_DATA and TRAVEL are neutral. Two implementations of one rule is already one too many,
so it is written to match line for line, and the migration says in a comment that if the two ever
disagree, the device is right and the SQL is the bug.

The suite pins this rather than trusting it: the seed is KEPT, KEPT, MISSED, KEPT and check 5
asserts the streak reads `1,2,0,1`. A naive implementation that counted KEPT nights would produce
`1,2,2,3` and fail — which is the point of choosing that seed.

The streak is scoped to the pod's `cycle_start_date` (D-006). A streak that ran across cycle
boundaries would not be the thing D-006 describes.

## 4. Pod size 3–8, in the database

**Upper bound: a `before insert or update` trigger** (`enforce_pod_size`) that counts active
members excluding the row being written — the exclusion matters, or an UPDATE of an existing
member would count them twice. A ninth active member raises `check_violation`. It is
`security definer` so the count sees the whole pod regardless of the caller's RLS.

**Lower bound: not a constraint, and it cannot be one.** Every pod passes through one and two
members on its way to three, so a check demanding `>= 3` would make pods impossible to create.
Saying this plainly is better than implementing something that looks like enforcement: the
minimum is a *readiness* rule, exposed as `pod_is_ready(pod_id)`, and the moment it means
anything is when a cycle starts. That is T-004B. There is no earlier point at which a pod having
two members is wrong.

Other rules pushed into the database rather than the app:

| Rule | Mechanism |
|---|---|
| One reaction per (from, to, night) | `unique` constraint — not app logic, which two taps can race |
| Witness must be in the same pod | Composite self-FK `(pod_id, witness_user_id) → (pod_id, user_id)` |
| Witness must not be self | `check (witness_user_id is distinct from user_id)` |
| Only the named witness may react | `with check` on the insert policy, not a client-side test |
| No reaction editing | No UPDATE policy at all — otherwise one-per-day is sidestepped by editing |

The composite FK carries a subtlety worth naming: it uses column-scoped `on delete set null
(witness_user_id)` (Postgres 15+; this project runs 17.6). A plain `on delete set null` would
null **both** referencing columns, and `pod_id` is `NOT NULL` — so removing a member who was
someone's witness would have errored instead of clearing that person's witness slot. I wrote it
the wrong way first and caught it on review; it is untested until the migration runs.

**A repository hazard found while applying this, worth more attention than it looks.** The

migration is reviewed in the repo and never applied — or, worse, where what is applied differs
from what was reviewed. It needs a fix (track the CLI directory, symlink it, or generate one from
the other) and it is not T-004A's to make.

## 8. Assumptions, unresolved issues, risks

**The open dependency the task names, restated because it is the biggest one.** Which wearables
the gym cohort actually owns is unknown. If a meaningful share cannot write sleep to Health
Connect, most nights are NO_DATA, and a witness feature whose entire content is KEPT / MISSED /
NO-DATA degrades into a feed of "no data" — which is not an accountability mechanism, it is a
reminder that the product does not work for you. **Nothing in this schema is designed around a
guess about that**, and nothing here should be taken as evidence the feature will land. It needs
an answer before T-004B designs screens on top of it.

**Now settled by the checker (2026-09-08).** TRAVEL → NO_DATA is **confirmed for v1**: D-005
grants three states and TRAVEL is not one of them. Reaction kinds are settled by **D-043** — one
kind, `SEEN`, because the thesis under test is that being witnessed changes behaviour, and
judgement stays out of the loop until that is measured.

**D-042 leaves a contradiction in the app that this task could not fix.** D-042 retires the brand
allowlist: Health Connect is the gate, and any device whose app writes sleep sessions counts. But
`app/src/eligibility/source-allowlist.v2.json` and `app/src/eligibility/index.ts` still implement
allow / unverifiedBrand / block lists, and `eligibility 13/13` still passes because it tests the
old rule. T-004A is SQL-only (AC-4A.8), so I have not touched them. **As it stands the app will
still refuse devices D-042 now admits** — including the boAt and Noise watches the mixed-brand
cohort is likely to be wearing. That needs its own task, and it belongs before any beta invite.

**Still unresolved:**

1. ~~The untracked CLI migrations directory (§5).~~ **CLOSED by D-044**: `backend/migrations/`
   is deleted and `backend/supabase/migrations/` is now the single tracked, canonical directory.
   The identical hazard remains for `backend/functions/` and is recorded in D-044 rather than
   fixed, since a wrong function deploy fails loudly where a missing migration failed silently.
2. **`pod_invites` has creator-only SELECT.** Redeeming an invite means reading a row you do not
   yet have access to, which needs a security-definer accept function. That belongs to T-004B
   with the rest of invite delivery; guessing at it now would be schema shaped around an unwritten
   flow.
3. **Cycle rollover at day 28 is still unwritten** (T-004B, and it needs a product decision
   first). The schema carries `cycle_start_date` and `cycle_length_days` and deliberately takes
   no position on what happens when a cycle ends.

**Risks:**

- **NO_DATA is now a certainty, not a risk** (D-042): the founder confirms the gym cohort wears
  mixed brands. A witness feed whose entire content is KEPT / MISSED / NO-DATA will show NO_DATA
  often, and if T-004B renders it as an error or an empty slot the feature reads as broken rather
  than as honest. It has to be first-class, with plain copy, and each user must learn on day one
  whether their device is feeding Zenoho — before they are being witnessed, not after a week of
  blank rows.
- The suite proves denial for one witness, one peer, one outsider and anon. It proves nothing
  about a member in two pods, or a witness who has left the pod. Both become reachable once
  T-004B can create pods, and neither is covered.
- `is_pod_member` is `security definer` to stop the `pod_members` policy recursing into itself.
  That is necessary, and it is also a function that sees all memberships; it returns only a
  boolean, and it is revoked from anon.
- A member sees their pod's full roster. That is the minimum the witness feature needs — you must
  see who is in the pod to name one of them — and it exposes membership, not nights.

**Recommended next step:** the D-042 app contradiction, as its own task, before T-004B. The
schema is done and proven; the thing that will actually stop a gym member joining is an
eligibility allowlist that no longer matches the decision. It is also the shortest path to
learning whether NO_DATA will dominate the witness feed — which is the assumption T-004B's whole
design rests on.
